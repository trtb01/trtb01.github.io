html tools: structure notes

REF :: oracle.html / trtb-dap.html / trtb-dice.html

This document records the structural findings of three tools built within this collection: the oracle, the audio protocol, and the dice engine. It is a neutral account. No judgments are made regarding merit or quality. The observations are limited to what the source documents contain.

1. shared conventions

The three tools share a common base. Each is a single HTML file using no framework. Logic is written in vanilla JavaScript, scoped within immediately-invoked function expressions. Styling is inherited from a shared stylesheet which defines the visual variables used throughout.

The following conventions are present in all three files:

conventiondetail
shared stylesheet/trtb.css (v3.0.0), accessed via <link>
themingdata-theme attribute on root element; toggles between light and dark
color variables--accent, --bg, --fg, --dim, --border-width
header#trtb_header containing page title and date
footer#trtb_footer containing copyright and a [b/w] toggle

containercontent resides in #app_container

2. oracle.html

FILE :: oracle.html

The oracle is a decision-support tool. It produces a d100 outcome and a d10 modifier. The interpretation is left to the user, guided by a static manual. The document is organised into four modules, each containing its own script block.

2.1 modules

moduleidfunction
display#module_displayrenders the d100 and the modifier
controls#module_controlsinitiates a roll on button press
settings#module_settingsmanages shake and voice options
help#module_helpstatic interpretation table

2.2 roll logic

The roll procedure is deterministic in structure, random in outcome:

d100 = floor(random() * 100) + 1
d10  = floor(random() * 10) + 1
coin = random() greater than 0.5
modifier = coin ? +d10 : -d10

The modifier is applied to the d100 before comparison with a target. A coin flip determines the sign of the modifier; no weighting is applied.

2.3 voice output

When enabled, the outcome is spoken via the Speech Synthesis API. Prior utterances are cancelled before a new one is issued. The speaking rate is fixed at 1.1.

2.4 shake detection

An optional gesture triggers a roll. Acceleration data is read from the device motion events. A speed value is computed from the difference in acceleration over a time interval. A threshold and a cooldown prevent repeated firing. iOS permission is requested conditionally when the API exposes requestPermission.

3. trtb-dap.html

FILE :: trtb-dap.html

The audio protocol is a media player. It accepts a local file or a remote URL and renders a live frequency visualisation. The document contains a single module assembled from inline-styled sections.

3.1 layout

The player is a column flex container with three regions:

regioncontent
headercollapsible source loader, file and URL inputs
bodycanvas visualisation and vertical title sidebar
controlsplay/pause and repeat toggle

The title sidebar uses writing-mode: vertical-rl to orient the track name vertically within a fixed-width column.

3.2 audio graph

On initialisation, an AudioContext is created. A media element source is routed through an analyser node to the destination. The analyser operates with an FFT size of 64.

source node -> analyser -> destination (fft: 64)

3.3 visualisation

A recursive render loop driven by requestAnimationFrame redraws the canvas each frame. The canvas is resized to its parent each pass. Frequency data is read via getByteFrequencyData into an unsigned byte array. Bars are drawn with heights proportional to the normalised values. The background and bar colours are read from the computed styles of the document.

3.4 source handling

A local file is loaded via a Blob URL; a remote address is assigned directly. The audio element carries a crossorigin attribute. Playback initiates automatically after a source is activated.

4. trtb-dice.html

FILE :: trtb-dice.html

The dice engine is a parsing and evaluation tool. Text input is interpreted as dice notation, resolved to a numeric result, and appended to a history list. It is the most computationally involved of the three files.

4.1 parser

Dice expressions are matched by a regular expression and replaced in place with their summed result. The pattern:

/(\d*)d(f|%|\d+)(!)?((?:k|kh|kl)\d+)?/gi

Supported notation:

notationmeaningimplementation
d%percentile / d100100 sides
dffate died3 mapped to -1/0/+1
dNdie with N sidesdirect roll
!exploding diere-roll on max, limit 50
k/kh/klNkeep highest / lowest Nsort and drop remainder

An explicit count prefix is supported. A count exceeding 500 is reduced to 500. Fate dice subtract 2 from each roll after rolling a d3.

4.2 evaluation

After substitution, the remaining string is filtered to numeric operators only and evaluated. Non-integer results are rounded to two decimal places. Each sub-expression produces a human-readable breakdown of individual rolls; kept rolls are summed, dropped rolls are marked with strikethrough styling.

4.3 query handling

Input is split on commas. Each sub-query is resolved independently. Results are joined with a vertical bar; breakdowns are joined with a double bar. An empty submission recalls the last successful query.

4.4 history

Completed rolls are inserted at the top of a scrollable list. Each entry contains the original query, the resolved result, and the roll breakdown. The list is capped by vertical scroll rather than item count.

5. communication patterns

No global state is used. Modules interact with one another through two mechanisms documented here.

5.1 methods attached to elements

A module may expose a function by assigning it to its own DOM element or a child. Other modules retrieve that element and invoke the function. The intent is portability: the logic is scoped to its container and does not leak into the global namespace.

element.triggerRoll = performRoll;
element.getTTSState = function() { ... };
element.updateValues = function(d100, mod) { ... };

5.2 sibling access

Cross-module state (such as a checkbox value) is read by locating the sibling element by identifier at call time rather than by holding a reference. This decouples the modules from one another's internal details.

6. summary

The three tools follow a consistent template. Each is a self-contained HTML document with scoped JavaScript, shared styling, and a common header/footer arrangement. They differ in purpose and complexity.

The oracle is modular and gesture-aware. The audio protocol is a single visual container wrapping the Web Audio API. The dice engine is a text parser with the most involved logic. Communication between parts is achieved by attaching functions to DOM elements and reading siblings by identifier.

No assertions are made about performance, accessibility, or maintainability. The above is a record of what the source documents contain.
